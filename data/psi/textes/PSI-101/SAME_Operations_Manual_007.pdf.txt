2.0 IN-FLIGHT FUNCTIONAL CHECKLIST 
This is a list of items that should be addressed after the hardware is installed in the MSG and before any 
samples are tested.  Not currently in any order. 
- Perform piston calibration and alter registry values as necessary.  See procedure later in this 
document.  Run a test with heater setpoint below R0 and no use of the thermal precipitors in order 
to confirm correct calibration. 
- Figure out good values for STSPumpFailureLowLimit and STSPumpFailureHighLimit registry 
values.  These depend somewhat on atmospheric pressure and should be adjusted for the ISS 
environment.  Correctly set, these values help detect failure of the STS pump. 
- Log some data with the P-Trak and DustTrak and confirm that their settings are correct.  For 
example: log interval, time constant, and date/time. 
- Record some video, downlink, and examine. 
- Experimentally determine the maximum setpoints that the mass flow controller will meet given 
ISS vacuum and GN2 sources.  Determine if any desired inlet velocities or diagnostic 
combinations are affected. 
- The registry value, DisableChecksumCheck, can be set to 1 to avoid the startup delay associated 
with calculating the checksum each time. 
- Revisit the decision about whether the heater controller offset correction will be done 
automatically as part of the test sequence or manually using the HeaterCorrectOffset utility prior 
to the test sequence.  Adjust the CorrectOffset registry value appropriately.

4.0 TEST CHECKLIST 
This is a list of important things to do or confirm pr ior to, during, and after the running of a sample test.  
Placement of a highly visible printout of this lis t on console is recommended.   Steps depend on whether 
sample heater offset correction is being done automatically or manually.  Check the CorrectOffset registry 
value to find out (0=manual, >0=automatic). 
- Once per carousel open the gate valves and turn on the diagnostics for TBD minutes.  Downlink 
the data and verify correctness. The purpose is to collect baseline measurements of the MSG work 
volume required by the science team. 
4.1 With Automatic Heater Offset Correction 
- Power on the system, wait for telemetry reception. 
- Send the Initialize command. 
- If the desired sample is not engaged, engage it using the Self Test command. 
- Turn on the 12VDC Heater Power. 
- Note the sample resistance and compare to ground measured resistance.  If they differ 
significantly, TBD.  Determine the setpoint. 
- Look at test parameters and change as necessary.  Use manual positioning option, but carousel and 
sample number must be correct. 
- Start the test. 
- When the test pauses check the following: 
o A “sample type is confirmed” message appears in the log. 
o The offset correction returned a value less than 50uV in the log. 
o The sample resistance is still good.  Within TBD % of before. 
o The desired diagnostics are powered and readings are nominal. 
o GN2 regulated pressure and vacuum pressure are good.  Range is TBD. 
- If the offset correction returned a value greater than 50uV, abort the test and restart.  If the offset is 
still greater than 50uV, change the CorrectOffset registry value to 0 (manual) and use the manual 
heater offset correction checklist instead. 
- Resume the test. 
- Watch the log for details about when the sample heater will start.  When it does, be ready to send 
an Abort command. 
- Watch the sample resistance and compare to the desired setpoint and MaxRt.  The software will 
too, and will abort heating if the resistance/temperature gets too high.  But watch anyway and send 
the Abort command in the highly unlikely event of too high resistance/temperature. 
- After sample aging, during exhaust, watch the output of the diagnostics for unexpected results. 
- After test is complete, power on any P-Trak or DustTrak that was used and retrieve the latest 
logged test ids.  Turn back off. 
- As desired, force a transfer of the current housekeeping and log files to the MLC.  Their transfer 
during power down has a slight chance of failing.  Doing it here ensures success. 
- Perform any other desired OS or system maintenance, such as directory listings or self tests. 
- Disengage the sample. 
- Send the Shutdown command with Shutdown option and power off system, or proceed to next 
test.

5.1 Initialization 
Select the Initialize button on the System tab, sending the Initialize command, and wait until the Run 
Mode changes from Unitialized to Ready. 
5.2 Setting parameters 
From the Testing tab, select Change… to change to the set of test parameters you want to look at.  Create 
a new test by selecting the CreateNew button.  Select Set anywhere in the window to change the 
parameter for the selected test. 
The Test Setup group box is the way to choose which di agnostics to use.  Select the Pri. or Sec. radio 
button to see the difference in setup between primary and secondary aging.  
Heater Control Setpoint should be set after knowing the unheated resistance of a sample, a.k.a. R0.

5.3 Registry File Concerns 
Assuming you’ve set the test parameters to a specif ic carousel number, sample number, heating setpoint 
and duration, you may think you are ready to go.  Y ou may not be.  There are a bunch of sample-related 
limit checks that may cause an error or warning prior to heating.  There are also many timing constants 
that affect the system behavior.  These can be cha nged by selecting Set Registry… on the System tab.  
See SAME-DOC-005, Software Interface Control Document  for key names and descriptions. A system 
timing simulator, currently located in SAMEFluidMode l.xls, will be available on console to help see the 
effect of registry value changes.  Testing with the engineering unit is also recommended. 
Alternately, registry values can be changed by editing the registry.txt file on the DACU.  This file is 
located in the /config directory.  Also in that dir ectory is registry.orig.txt which contains the original 
registry settings. 
Important:  Changes to registry values will not take e ffect until you restart the software.  Follow the 
steps for shutting down, below, but use the restart parameter option.

5.4 Running the Test 
From the Testing tab select Start… and enter the test number to run, if it hasn’t already been entered in 
the field, and select Send. 
After sample positioning and aging chamber setup has occurred the test will pause so you can examine 
the log for any warnings or errors.  Then send the Resu me button.  The test should proceed to finish.  You 
can abort anytime by sending the Abort command.  An abort causes all valves to be turned off as well as 
all diagnostics. 
5.5 Shutdown 
It is recommended that the system be gracefully shut down using the Shutdown button on the System tab, 
then cut power about 2 minutes later.  Current housek eeping and log files are transferred to the laptop 
during the first minute.  Use the second minute to ensu re that the system did not restart, looking for the 
restart of low rate telemetry packets and updating GMT.   If the system restarts, select Shutdown again or 
send the OS command with parameter, ‘/bin/shutdown –b’.

6.1 Transferring files from DACU to the MLC 
All files will be automatically transferred from th e DACU to C:\ftp on the MSG laptop.  Housekeeping 
files (.hkp) are transferred on the hour and upon shut down (with either the shutdown or restart option).  
The Log file is also transferred upon shutdown.  P- Trak, DustTrak, and heater files are transferred soon 
after they are created.   P-Trak and DustTrak file s are not automatically created since their data is 
embedded in the housekeeping data.  To explicitly retrie ve logged data select the Transfer Data button on 
the DustTrak and P-Trak tabs.  This should be do ne no more frequently than once per minute because the 
filename is derived from the GMT, including the latest minute, but not the latest second.  
If you need the data immediately or a file doesn’t get downlinked for some reason you’ll have to do it 
manually using one of two methods described here: 
6.1.1 Using SAMEDisplay and FTP Cmd command. 
You’ll need to identify what file you need and the dir ectory it is in.  Files are stored in a directory named 
according to GMT year and day.  For instance /data/2006_132/.  The .log file will be named 
2006_132_00.log in this example.  Housekeeping files will be 2006_132_15.hkp,  2006_132_16.hkp, etc. 
according to the GMT. 
With the flight software and SAMEDisplay running (does not need to be Initialized), select the FTP Cmd 
from the System tab.  Type:  LCD /data/2006_132, for example, to change local directory (on the DACU) 
and send the command.  Then select FTP Cmd again a nd type:  PUT 2006_132_16.hkp, for example, and 
send the command.  Watch your letter case – it matters. 
6.1.2 Using SAME processor command line to transfer files 
For this to work you’ll need a keyboard and mon itor connected to the GSE port on the SAME DACU.  
Also, verify that the switch on the SAME DACU is sw itched to Override position.  This is obviously a 
ground use only method. 
From the command line on the GSE monitor (if the so ftware is running you can get another console 
window by typing <CTRL><ALT>n, where n is 1 or 2), na vigate using cd and ls to the directory with the 
file you want to transfer.  Type:  ftp 192.168.1.1 <Enter>.  Type: anonymous<Enter> for name and just 
<Enter> for password.  Then at ftp> prompt t ype: bin<Enter>, then t ype: put 2006_ 132_16.hkp, for 
example.  File should end up in C:\SAME Data on laptop.  After done transferring file(s), type: 
bye<Enter> on the DACU. 
You can also use the two above methods to transfer files to the DACU using GET and get instead of puts.

7.3 Piston Calibration 
Piston calibration, a.k.a. piston characterization, is a process of adjusting some registry values so that 
piston rates and time marks are correct for current  conditions.   This process should be performed 
whenever there is a change of hardware, especially  the aging chamber and piston itself; a change of 
environment, such as the move to the ISS; a change of fluid source strength; or a change of hardware 
condition, perhaps after many tests have been run.

7.3.2 Sample Heating Start Time 
Ideally, the start of sample heating is calculated so that  the end of sample heating occurs before the piston 
reaches the top of the chamber.  Actually, even before that, so that most of the smoke in the inlet tube at 
the end of heating enters the chamber as well.  And really, even before that, so that some clean air follows 
the ‘last’ of the smoke and more of the smoke enters the chamber.  The amount of the latter clean air is 
determined by the BackEndCleanAirOffset registry value. 
Because there is no direct physical measurement of where the piston is in the middle of its stroke, the 
software must estimate when the stroke begins and how long the stroke will take.  Then it can back off 
from there to determine sample heating stop and start times.  The registry values, FillWaita.b, where a.b is 
0.0 to 5.0 by 0.5, help compensate for timing inconsis tencies which are a function of fill rate in LPM.   
(These values were more drastically a function of f ill rate before the FillLeakRateLPM registry value was 
increased from 0.0.  See section 7.3.1.).  
Piston chamber fill movement begins by evacuating the the drive side of the piston at a rate of 3.0 LPM 
until the drive side pressure reaches 13.2 psia.  These values have been determined to be reliable, but can 
be changed if necessary by altering the registry values, FillStartRateLPM and FillStartPressurePSIA.  
Then the software waits for a period determined by th e desired fill rate, a function of inlet velocity, and 
the FillWait registry values.  For a fill rate of 3.0 the software waits for the value of FillWait3.0.  For rates 
in between, the wait time is interpolated.  After wai ting this time the software marks the start of piston 
movement, logging a message for the user.  Sample  heating and other start and stop times are based on 
this mark.  To determine the best FillWait registry values, 
- Perform the following steps for each rate, R= 0.5 to 5.0 by 0.5, and then estimate FillWait0.0 
interpolating by hand on a graph of the other values versus rate. 
- Fill the chamber using the SelfTest command and the rate. 
- Note when the drive side pressure reaches 13.2 psia.  The software issues a “x seconds before 
piston moving mark” message to indicate this point.  The aim of this procedure is to get the ‘x’ 
right. 
- Note when the piston reaches the top of the chamber.  Visual confirmation is best, but 
examination of the drive side pressure also works.  The start of the drastic drop in pressure is the 
point at which the top is reached.  Do not rely on the “Aging chamber is filled” log message.  
This comes only after the FillTopPressurePSIA has been reached.

7.3.3 Secondary Aging Volume 
When a secondary aging period and volume are speci fied, the piston must stop a percentage of the 
distance between the top and bottom of the chamber.  There is no direct physical measurement of the 
running distance, therefore it is estimated from th e exhaust rate over time.  The registry value, 
ExhaustPercentageCorrectionFactor, is applied to the running percentage.  To adjust this value, 
- Perform a SelfTest to exhaust the chamber to a specific percentage.  For best results use the 
exhaust rate and secondary volume  that will be used during the actual test.  Or use 5 LPM and 
50%. 
- Perform a SelfTest to exhaust the chamber the rest of the way.  Use the same rate and 100%. 
- Calculate the time taken for each portion using log messages or pressure data and figure the 
percentage of total time taken by  the second exhaust.  Adjust the registry value and repeat until 
this percentage is within the desired accuracy of the secondary aging volume percentage. 
7.3.4 Exhaust Rate 
It was verified that the system exhausts at a rate sufficient to achieve overpressure of the diagnostic duct 
for all combinations of diagnostic use except when usi ng the STS detector with both DustTraks.  If this 
situation changes, the exhaust rate can be increased using the ExhaustOverpressureRate registry value.

7.5 Description of HeaterCorrectOffset Utility 
Sample heater offset correction is a feature of the sample heater microcontroller that reduces 
measurement error by automatically removing off set voltages from the signal path.  After offset 
correction is performed, all subsequent resistance me asurements will include the o ffset correction.  Until 
the system is powered off, that is.  At power up the offset correction is zero.  Offset correction should be 
run for each sample while the sample is engaged with the inlet tube and sample heater contacts. 
Occasionally the offset correction circuitry produces a co rrection that is obviously too high.  The result is 
that subsequent reports of resistance are lower than ac tual.  This can be detected at the time of the test 
pause by looking at the sample resistance and by lo oking for the log message indicating the value of the 
offset correction.  It should be approximately 200uV or less. 
If the offset correction at the time of the test pause is too high, then the test must be aborted and restarted 
to give the offset correction circuitry a second chan ce.  To avoid this time-consuming detour a utility 
separate from the flight software has been developed.  It is HeaterCorrectOffset_g in the /root directory of 
the DACU.  It can be run from the flight software by sending the OSCommand command with a 
parameter of ‘/root/HeaterCorrectOffset_g’. 
The HeaterCorrectOffset utility app lies 12VDC to the sample heater , waits a few seconds, and then 
requests an offset correction from the heater microcontro ller.  If the returned off set is in range then the 
utility exits, otherwise it requests the offset correction ag ain for several times until it is in range.  Either 
way, 12VDC is removed from the sample heater befo re the utility exists.  As long as system power (not 
12VDC) remains applied, the offset correction initiated by  the utility will be used by the flight software.  
If the utility fails to correct the offset  to within the desired range then it returns a -1 (which is reported in 
the flight software log as 65280), otherwise it returns a zero to indicate success. 
There is one caveat to running the HeaterCorrectOffset utility.  The flight software must be either not 
running, which will not occur during flight, or must be in the uninitialized state.  Once the software is 
initialized the utility cannot gain serial access to the heater micr ocontroller.  Thus the sequence 
gymnastics in section 4.0. 
Additionally, if the HeaterCorrectOffset utility is used, then offset correction prior to the test pause should 
be disabled.  Otherwise an incorrect correction he re will negate the use of the utility.  Setting the 
CorrectOffset registry value to zero will disable au tomatic offset correction during the test, allowing the 
value created by the HeaterCorrectOffset utility to be used.

7.7 Use of tar utility 
The tar utility can be used to assemble or disassemble collections of files on the DACU, much like 
WinZip does on a PC.  It may be useful to tar a collection of files into one file prior to downlink.  The 
executable is located in the /root directory on the DACU and therefore should be able to execute from any 
local directory.  It is not necessary to specify the path to tar.  Use the OSCommand and parameters 
according to http://www.qnx.com/developers/docs/6.3.0/neutrino/utilities/t/tar.html.

8.0 KNOWN ISSUES 
- Aborting a test occasionally causes the software to restart.  If this should happen you’ll need to 
reissue the Initialize command. 
- Try to avoid running a test sequence through the change of hour (i.e. 12:45-13:05).  Transfer of 
the housekeeping file at the top of the hour takes a good bit of processor time and the processor is 
close to 100% capacity, possibly affecting diagnostic measurement retrieval. 
- It is recommended that the system be gracefully shut down using the Shutdown button on the 
System tab, then cut power about 2 minutes later.  However, about 20% of the time the software 
will hang or restart before completely shutting down.  If it restarts, issue the Shutdown command 
again or issue the OS command with parameter, ‘/bin/shutdown –b’.   If it hangs (you may only 
know this if you have a monitor connected to the GSE port) a hard power off will have to suffice.  
The operating system will clean up any file ‘litter’ on the next power up. 
- Maximum inlet velocity with the FillLeakRateLPM registry value equal to 0.30 is 9.8 cm/sec.  
Above this the software does not correctly use the FillWait registry values to time chamber fill 
operations, including sample heating start time.  10.0 cm/sec can be achieved if FillLeakRateLPM 
is 0.25 LPM or less.  But timing is affected in other ways and ground testing or flight testing 
without sample heating is recommended. 
- Whenever the P-Trak is on, the DACU requests a measurement from it once per second.  
Occasionally the P-Trak does not respond with a measurement and the DACU substitutes a -999 
value instead to mark this occurance.  If the P-Trak is logging during this time, that missing data 
can be recovered by issuing the Transfer Data command to retrieve the logged data. It is 
recommended that this be done for each test, soon (within days) after the test is complete. 
- The P-Trak memory can hold approximately 60 20-minute tests.  When all memory is used the 
unit does not respond with any serial measurements while logging.  In other words, continuous -
999 readings is one indicator of full memory.  It is suggested that memory be cleared after 50 
tests to be safe. 
- Sample heater offset correction occasionally produces an incorrect correction factor.  The result is 
that reported sample resistance is lower than actual.  For more information see section 7.5. 
- Using ground support equipment there was insufficient fluid flow during chamber exhaust to 
maintain overpressure of the diagnostic duct, as required, when the STS detector and both 
DustTraks are in use.  When the STS detector is used it is recommended that at most one 
DustTrak is used. 
- If the heater gives an “Abort on MaxRt” error, the system must be power cycled before 
proceeding.  Otherwise, as will be apparent, the resistance measurement will be in error. 
- When specifying inlet velocities below 2 cm/sec, the FillWait registry values may not be 
accurate.  The registry value, BackEndCleanAirOffset, must be adjusted to ensure correct heater 
timing.  For 1 cm/sec, a value of 170 seconds is good.  But run a test with no heating to be sure. 
- During ground testing the connection between the DACU and the MSGSimulator occasionally 
drops out.  Packet count numbers of the MSGSimulator no longer increment and change from 
green to blue. To reestablish the connection deactivate it and activate it again.
